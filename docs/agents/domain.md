# Доменные доки

Как инженерные скиллы должны использовать доменную документацию репозитория при изучении кодовой базы.

## Перед исследованием прочитать

- **`CONTEXT.md`** в корне репозитория, или
- **`CONTEXT-MAP.md`** в корне, если существует: он указывает на один `CONTEXT.md` на контекст; читать относящиеся к теме.
- **`docs/adr/`**: читать ADR, затрагивающие область работы. В multi-context репозиториях также смотреть `src/<context>/docs/adr/` для решений уровня контекста.

Если каких-то файлов нет — **продолжать молча**: не отмечать отсутствие и не предлагать создавать заранее. Скилл `/domain-modeling` (через `/grill-with-docs` и `/improve-codebase-architecture`) создаёт их лениво, когда термины или решения реально фиксируются.

## Структура файлов

Single-context репозиторий (наш случай):

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-....md
│   └── 0002-....md
└── src/
```

Multi-context (при наличии `CONTEXT-MAP.md` в корне): `CONTEXT-MAP.md` + `docs/adr/` (системные решения) + `src/<context>/CONTEXT.md` и `src/<context>/docs/adr/` для каждого контекста.

## Использовать словарь глоссария

Называя доменное понятие (в заголовке issue, предложении рефакторинга, гипотезе, имени теста), используйте термин так, как он определён в `CONTEXT.md`. Не уходите в синонимы, от которых глоссарий явно предостерегает.

Если нужного понятия в глоссарии ещё нет — это сигнал: либо вы изобретаете язык, которого проект не использует (передумайте), либо это реальный пробел (отметьте для `/domain-modeling`).

## Отмечать конфликты с ADR

Если ваш результат противоречит существующему ADR, укажите это явно, а не молча игнорируйте:

> _Противоречит ADR-0007 (…), но стоит переоткрыть, потому что…_
